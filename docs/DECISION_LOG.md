## 결정 기록

### 2026-10-16 · 백업 오프사이트 자동화 (S3 호환)

- **배경**: 일일 백업은 같은 Fly 볼륨에 있어 **볼륨 자체 유실**에는 무력했다(이전 결정에서 "다운로드로 수동 오프사이트"로 두고 미룬 과제). 자동 오프사이트가 필요.
- **결정**: 백업 생성 직후, 환경변수로 **S3 호환 스토리지**(AWS S3 / Cloudflare R2 / Backblaze B2)가 설정돼 있으면 자동 업로드. **boto3 없이 표준 라이브러리만으로 AWS Signature V4(path-style PUT)** 구현(`backup_offsite.py`). 베스트에포트(실패해도 로컬 백업·서비스에 영향 없음).
- **이유/철학**:
  - *외부 라이브러리 0 유지*: 프로젝트 원칙(표준 라이브러리만)에 맞춰 SigV4를 직접 구현. requirements를 늘리지 않음.
  - *정확성은 공식 테스트벡터로 보증*: AWS 문서의 **서명키 파생 예제**(`c4afb1cc…`)와 **SigV4 test-suite get-vanilla 최종 서명**(`5fa00fa3…`)에 내 구현이 일치함을 테스트로 고정 → 서명 로직이 스펙과 동일함을 증명.
  - *설정 없으면 완전 무동작*: 네 개 env(endpoint/bucket/access/secret)가 다 있어야 활성. 미설정이면 조용히 건너뜀(기존 동작 불변).
  - *path-style*: 버킷을 경로에 두는 방식(`endpoint/bucket/key`)이 R2·B2·S3 모두에서 통일되게 동작.
- **대안(기각)**: boto3 추가(의존성·용량 → stdlib SigV4), presigned URL 업로드(서버가 직접 PUT이면 불필요), 전용 백업 SaaS(계정·비용 → 사용자가 가진 S3 버킷 재사용).
- **구현**: `backup_offsite.py`(`is_configured`/`signing_key`/`build_authorization`/`upload_file`). `server.py` `_offsite_upload()`를 자동 백업 루프·관리자 수동 백업 직후 호출, `/api/admin/backups`에 `offsite` 플래그, admin 안내에 상태 표기.
- **운영**: `BACKUP_S3_ENDPOINT`·`BACKUP_S3_BUCKET`·`BACKUP_S3_ACCESS_KEY`·`BACKUP_S3_SECRET_KEY`(+선택 `BACKUP_S3_REGION`/`BACKUP_S3_PREFIX`). Fly: `fly secrets set ...`.
- **검증**: AWS SigV4 공식 벡터 2종 일치, 모의 S3 서버 대상 실제 PUT(경로·Authorization·content-sha256·본문) 검증, 미설정 시 무동작 — 테스트 통과.
- **상태**: ✅ 완료. (운영자가 S3/R2 버킷·키 설정 시 자동 동작)

### 2026-10-16 · 결제 후속 (부분환불 · 카드변경 · 영수증 · 구글 동의)

- **배경**: 결제 기본기는 됐지만 운영에서 자주 필요한 부분환불, 카드 교체(갱신 실패·카드 만료 대응), 영수증 제공, 그리고 구글 가입자 약관 동의 기록이 빠져 있었다.
- **결정 및 구현**:
  - **부분환불**: 관리자 취소에 `amount` 추가. 잔액 미만이면 토스 `cancelAmount`로 부분취소하고 `payments.refunded_amount` 누적(요금제 유지), 잔액 이상이면 전액취소(CANCELED + free 회수). `add_refund()`가 누적·전액여부·잔액을 반환.
  - **카드 변경**: `/api/billing/change-card` → `requestBillingAuth`(successUrl `mode=update`) → `auth-confirm`이 **빌링키만 교체**(청구·플랜·다음청구일 유지, `update_billing_key`). past_due였다면 active로 복구.
  - **영수증**: 토스 승인/청구 응답의 `receipt.url`을 `payments.receipt_url`에 저장. 자체 영수증 페이지 `/receipt/<order_id>`(로그인·본인·인쇄 가능, 사업자정보 포함) + 설정 "결제 내역"에서 링크.
  - **구글 가입 동의**: 구글 OAuth 신규 가입 시 `agreed_terms_at` 기록(로그인 화면의 약관 동의 고지를 근거로 한 묵시적 동의).
- **이유/철학**: *부분환불은 요금제를 건드리지 않음*(일부만 돌려준 것이지 구독 취소가 아님) — 전액일 때만 회수. *카드 변경은 과금 없이*(이미 결제한 주기를 다시 청구하면 안 됨) — 키만 교체. *영수증은 이중 제공*(토스 공식 + 자체 페이지)으로 세금·증빙 요구에 대응. *동의는 경로 불문 기록* — 이메일·구글 모두 `agreed_terms_at` 남김.
- **대안(기각)**: 부분환불 시에도 요금제 회수(과한 처벌 → 전액만), 카드 변경 시 재청구(이중과금 → 무청구), 영수증 자체발급만(법정 증빙 신뢰 → 토스 공식 URL 병기).
- **검증**: 구매·receipt 저장, 영수증 렌더·타인 404, 부분환불(요금제 유지·잔액)·잔액초과 거부·전액환불(회수), 카드변경(키 교체·무청구·무구독 400) — 테스트 전부 통과.
- **상태**: ✅ 완료. (백로그: 사용자 셀프 부분환불 신청 폼)

### 2026-10-16 · 운영 대시보드 — 매출·구독 지표 (MRR)

- **배경**: 결제·구독이 돌기 시작했는데 "지금 얼마 버는지, 구독이 몇 개인지"가 admin에 안 보여 의사결정이 어려웠다.
- **결정**: admin 상단에 **매출·구독 카드**를 추가 — **MRR**(활성 자동결제 구독의 월 요금 합), 활성 구독 수, 유료 사용자 수, 이번 달 매출/환불, 누적 매출, 결제 건수. `admin_global_stats()`에 집계 쿼리로 추가(별도 API 없이 기존 `/api/admin/stats`에 포함).
- **이유/철학**: *단일 출처*: 결제 원장(payments)과 구독 상태(users.sub_*)에서 직접 집계 → 별도 집계 테이블 없이 항상 정확. *MRR 정의 명확화*: MRR은 "자동결제 활성 구독의 월 요금 합"으로 정의(단건 결제는 반복이 아니므로 MRR 제외, 대신 당월/누적 매출에 포함). *매출=성공 결제, 환불 별도*: DONE 합을 매출로, CANCELED는 환불로 분리 표기(순매출 판단은 운영자가).
- **대안(기각)**: 별도 통계 테이블·배치 집계(복잡·정합성 부담 → 실시간 쿼리, 규모상 충분), 단건까지 MRR에 포함(MRR 의미 왜곡 → 반복 매출만).
- **구현**: `database.admin_global_stats()`에 paid_users·active_subscriptions·mrr·revenue_month·revenue_total·refunds_month·payments_done 추가. `admin.html` renderStats에 매출·구독 카드 섹션.
- **검증**: MRR(활성 구독 요금 합), 활성 구독·유료 사용자 수, 당월 매출(DONE 합)·환불(CANCELED 합)·누적, `/api/admin/stats` 포함 — 테스트 통과.
- **상태**: ✅ 완료. (백로그: 기간별 추이 그래프, 전환율·이탈률, 코호트)

### 2026-10-16 · 학습 리마인더 메일 (리텐션)

- **배경**: 간격 반복 학습은 "제때 다시 오는 것"이 핵심인데, 사용자가 복습 타이밍을 놓치면 학습(및 구독)이 끊긴다. 재방문을 유도할 장치가 없었다.
- **결정**: **하루 1회** "오늘 복습할 N개" 메일을 **복습할 항목이 있는 사용자에게만** 발송. 기존 SMTP 인프라 재사용. 지정 시각(UTC, 기본 0시=9시 KST)에 배치 발송하고 **사용자별 하루 1회**(`reminder_sent_on`)로 중복 방지. **원클릭 수신거부 링크**(토큰) + 설정 토글 제공, 기본 ON.
- **이유/철학**:
  - *보낼 가치가 있을 때만*: 복습 항목이 0이면 보내지 않음(스팸 방지·신뢰 유지). 미인증·정지·수신거부 사용자 제외.
  - *수신거부는 쉽게(법·신뢰)*: 메일 하단 원클릭 수신거부(로그인 불필요) + 앱 설정 토글. 정보통신망법상 광고성 아닌 서비스 알림이지만 옵트아웃은 기본 제공.

### 2026-10-15 · DB 백업 (데이터 유실 방지, C)

- **배경**: 전체 서비스 데이터가 Fly 볼륨의 **SQLite 단일 파일**(`/data/english_master.db`)에 들어 있다. 앱 버그·실수 삭제·마이그레이션 사고·볼륨 손상 중 하나라도 나면 전 사용자 데이터가 날아간다. 복구 수단이 전혀 없었다.
- **결정**: **앱 내장 자동 백업**을 도입한다. ① 매일 1회 **SQLite 온라인 백업 API**(`conn.backup`)로 **실행 중에도 일관된** 스냅샷을 `/data/backups/`에 생성, 최신 **14개**만 보관(롤링). ② `/admin`에서 **수동 백업·목록·다운로드·삭제**. 다운로드로 **오프사이트(운영자 PC) 보관**을 사람이 직접 할 수 있게 한다.
- **이유/철학**:
  - *외부 의존성 0*: 결제/계정이 필요한 S3·R2 등 없이, 표준 라이브러리(`sqlite3`)만으로 당장 돌아가는 보호막을 먼저 깐다(백로그 C의 "외부 의존성 없음" 조건).
  - *일관성 우선*: 파일 `cp`는 쓰기 도중이면 깨질 수 있다. `conn.backup`은 트랜잭션 일관 스냅샷을 보장하고 락 경합도 작다.
  - *다층 방어 명시*: 같은 볼륨의 백업은 **앱-레벨 사고**(버그·실수 삭제)는 막지만 **볼륨 자체 유실**은 못 막는다. 그래서 (a) 관리자 다운로드(오프사이트)와 (b) **Fly 볼륨 스냅샷**(인프라, 아래 운영 메모)을 **보완책으로 문서에 명시** — "백업 있으니 안전"이라는 착각을 경계.
  - *조용한 자동화*: 별도 cron 없이 백그라운드 스레드가 1시간마다 깨어나 "오늘 백업 없으면 1회" 생성. 기존 플레이리스트 동기화 루프와 같은 패턴이라 운영 모델이 일관.
- **대안(기각)**:
  - *Fly 볼륨 스냅샷만 의존*: 인프라 레벨이라 편하지만, 앱에서 "지금 백업/다운로드"를 못 하고 세밀한 복구 단위가 없다. 보완책으로는 쓰되 단독 해법으론 기각.
  - *외부 오브젝트 스토리지(S3/R2) 업로드*: 진짜 오프사이트지만 **계정·키·비용**이 필요 → 백로그 C의 "외부 의존성 없음" 위반. 다운로드(수동 오프사이트)로 대체하고, 자동 오프사이트는 PG 연동 이후 과제로 미룸.
  - *파일 복사(`shutil.copy`)*: 간단하지만 쓰기 중 비일관 위험 → 온라인 백업 API 채택.
  - *무제한 보관*: 볼륨이 꽉 참 → 14개(≈2주 일일) 롤링.
- **구현**:
  - `database.py`: `BACKUP_DIR=/data/backups`, `create_backup()`(온라인 백업+유일 파일명+자동 prune), `list_backups()`(최신순), `prune_backups(keep=14)`, `backup_path_if_valid()`(파일명 정규식 검증 → **경로탈출 차단**), `delete_backup()`, `latest_backup_date_utc()`.
  - `server.py`: `_backup_loop()`(1시간 주기, 오늘 미백업 시 생성) + `init_app`에서 `ENABLE_BACKUP`(기본 1) 가드로 기동. 관리자 API `GET/POST /api/admin/backups`, `GET .../<name>/download`(send_file, 파일명 검증), `DELETE .../<name>`.
  - `templates/admin.html`: "DB 백업" 섹션 — 지금 백업, 목록(파일/크기/시간), 다운로드·삭제, 자동/보관 안내.
- **운영 메모(오프사이트 보완)**: Fly 볼륨 스냅샷을 함께 켜두면 볼륨 유실까지 대비된다. 예) `fly volumes list` → `fly volumes snapshots list <id>`로 확인, 스냅샷 보존기간은 `fly volumes update <id> --snapshot-retention <days>`(기본 5일)로 조정. 단일 워커(Dockerfile `--workers 1`)라 백업 스레드는 1회만 돈다. 다중 워커로 늘릴 경우 한 워커만 `ENABLE_BACKUP=1`로 둔다.
- **검증**: 온라인 백업이 유효한 DB로 열리고 데이터 보존, 같은 초 유일 파일명, prune(keep) 동작, **경로탈출/잘못된 파일명 거부**, 관리자 API(목록·생성·다운로드 attachment·삭제)·비관리자 403 자동 테스트 **전부 통과**.
- **상태**: ✅ 완료·검증. (다음: 실결제 PG 연동)

### 2026-10-15 · AI 사용량 제한 (서버 공용 키 비용 보호, C)

- **배경**: 개인 API 키가 없는 사용자는 **서버 공용 키**(`SERVER_AI_KEY`)로 AI 분석(직독직해/문법/단어/퀴즈/단어뜻/연결 테스트)을 쓴다. 이 비용은 전부 운영자가 부담한다. 상한이 없으면 한 명이 수천 번 호출해 **비용 폭탄**이 날 수 있다. (유료 결제(PG) 연동 전이라 더 위험.)
- **결정**: **서버 공용 키로 처리되는 호출에 한해** 사용자별 **일/월 호출 한도**를 둔다. 한도는 **요금제(plans)별로 관리자 편집** 가능. 기본값 free 20/일·200/월 → max 500/일·10000/월.
  - 한도 규칙: **-1 = 무제한, 0 = 사용 불가, 양수 = 허용 횟수.**
  - **개인 키 사용자는 자기 비용이므로 무제한**(제한·기록 모두 안 함).
- **이유/철학**:
  - *과금되는 호출만 센다*: **캐시 히트·무료 사전(dictionaryapi) 폴백·개인 키 호출은 비용이 없으므로 카운트하지 않는다.** 실제 돈이 나가는 "서버키 + 캐시 미스 + 호출 성공"만 원장에 1 기록.
  - *비용 안전 우선(모호하면 막는 쪽)*: 한도 0을 "무제한"이 아니라 "차단"으로 정의. 관리자가 실수로 0을 넣어도 비용이 새지 않는다. 무제한은 명시적으로 -1.
  - *기존 할당량 철학 재사용*: 콘텐츠 등록 할당량과 동일하게 **append-only 원장(ai_usage_log)** + 요금제 테이블 컬럼으로 구현해 일관성 유지.
  - *은혜로운 저하(graceful degradation)*: 단어뜻(`/api/ai/word-meaning`)은 한도 초과 시 **에러 대신 무료 사전 API로 폴백** — 학습 흐름을 끊지 않는다. 반면 문장 분석(`/api/ai/action`)은 대체재가 없으므로 **429 + 친절 안내**(내일 다시/개인 키 등록/업그레이드).
- **대안(기각)**:
  - *글로벌(서버 전체) 한도*: 한 사용자가 전체를 소진시켜 다른 사용자를 막을 수 있음 → 사용자별 한도 채택.
  - *배경 워커(번역/사전캐시/뜻) 호출도 카운트*: 이들은 **전역 캐시 1회 생성**(모든 사용자 공유)이라 사용자별 비용 귀속이 부적절하고 콘텐츠 양으로 이미 유계 → **대상에서 제외**(콘텐츠 등록 할당량이 상위에서 억제).
  - *토큰/금액 단위 과금*: 정확하지만 복잡·공급자별 상이 → 호출 **횟수** 단위로 단순화(상한의 목적엔 충분).
  - *구독 기념일 기준 월주기(콘텐츠 할당량 방식)*: AI 한도는 비용 가드 성격이라 **캘린더 일/월(UTC)**이 더 직관적·단순 → 채택. (코드 전반이 UTC 기준이라 일관.)

### 2026-07-07 · 보안 강화 A-1 (세션 쿠키 + 로그인 brute-force)

**세션 쿠키 플래그**
- `HttpOnly`(XSS 시 쿠키 탈취 방지) + `SameSite=Lax`(CSRF 완화) 적용. `Secure`(HTTPS 전용)는 환경변수 `COOKIE_SECURE`로 제어 — 프로덕션(`fly.toml [env] COOKIE_SECURE=1`)만 켠다.
- *이유(Lax 선택)*: `Strict`는 구글 OAuth 콜백(외부→우리 사이트 리다이렉트 복귀) 시 세션 쿠키가 전송되지 않아 로그인이 깨진다. `Lax`는 최상위 GET 이동에 쿠키를 보내므로 OAuth와 호환된다.
- *이유(Secure 조건부)*: 로컬은 http라 Secure를 항상 켜면 개발 중 로그인이 막힌다. env로 프로덕션만 적용.

**로그인 brute-force 방지**
- IP 기준 인메모리 레이트리밋: 15분 창에서 실패 8회 초과 시 `429`로 일시 차단. 비밀번호가 맞으면 카운트 초기화(정상 사용자 잠금 방지).
- *한계(명시)*: `--workers 1` 전제(워커별 독립 메모리). 다중 워커/머신으로 확장하면 Redis 등 공유 저장소로 이전 필요. 프록시 뒤라 `X-Forwarded-For` 첫 값을 클라이언트 IP로 사용.
- *기각한 대안*: 외부 레이트리밋 라이브러리 — 의존성 최소주의에 맞지 않고, 현 규모엔 인메모리로 충분.

**상태**: ✅ 구현·검증 완료 (2026-07-07). 쿠키 플래그(HttpOnly/SameSite=Lax) + 8회 실패→9회차 429 확인.

   - *이유*: 의존성 최소주의. 외부 이메일 API(SendGrid 등)는 키·SDK가 필요. SMTP는 어떤 메일 계정(Gmail 앱 비밀번호, 회사 메일 등)이든 붙일 수 있어 운영자 자유도가 높다.

4. **최초 운영자(첫 가입자 = 관리자, id=1)는 자동 인증**

**정책 결정 3가지와 그 이유(철학)**

1. **결제 범위: "요금제·할당량 먼저, 실결제(PG)는 나중"**
   - *이유*: 실제 PG 연동은 결제사 가입·API 키·웹훅이 필요해 외부 의존성이 크다. 그 전에 요금제 데이터 모델과 한도 강제 로직을 완성해 두는 것이 순서상 옳다.
   - *현재 운영 방식*: 관리자가 `/admin`에서 사용자 요금제를 **수동 부여**한다. (PG가 붙으면 이 수동 부여를 결제 성공 이벤트가 대신하게 된다.)
   - *기각한 대안*: 지금 바로 토스페이먼츠/Stripe 연동 — 아직 결제사 미정, 키 없음.

2. **카운트 기준: "월 신규 등록 수" + "삭제해도 복구 안 됨"**
   - *이유(철학)*: 한도는 "지금 보유 중인 개수"가 아니라 **"그 주기에 새로 등록한 횟수"** 로 센다. 콘텐츠를 등록했다가 지우고 다시 등록하는 식으로 한도를 무한히 우회하는 것을 막기 위함이다. 등록은 실제 비용(자막 처리·AI 호출 등)을 유발하는 행위이므로, 등록 그 자체를 과금 단위로 본다.
   - *설계적 함의(중요)*: "삭제해도 카운트가 복구되면 안 된다"는 요구는 **영상 행(row)을 세면 안 된다**는 뜻이다(영상을 지우면 행도 사라지므로). 그래서 별도의 **등록 원장(ledger) 테이블** `content_registrations` 를 두고, 영상이 삭제돼도 원장 기록은 남긴다.
   - *멱등성*: 같은 콘텐츠를 (지우지 않은 채) 다시 등록하면 카운트되지 않는다. 원장의 `(user_id, video_id)` UNIQUE로 보장. 단, **지웠다가 다시 등록하면** 새 영상 id가 생기므로 새 등록으로 카운트된다(정책상 옳음).
   - *기각한 대안*: "동시 보유 수 기준"(삭제하면 슬롯 복구) — 우회가 쉽고, 등록 비용을 반영하지 못함.

3. **월 리셋 기준: "구독 시작일 기준"**
   - *이유*: 실제 결제 주기와 정확히 일치시키기 위함(가입/결제한 날부터 한 달). 달력 1일 기준은 구현이 단순하지만 결제 주기와 어긋난다.
   - *구현*: `plan_started_at`(구독 시작일)의 "가장 최근 매월 기념일"을 계산해 그 이후 등록 수를 센다. 짧은 달은 말일로 보정. 관리자가 요금제를 바꾸면 `plan_started_at`이 그 시점으로 갱신된다.

4. **free는 "평생 1개"의 철학**
   - free는 매월 리셋되지 않는다(`period_type='lifetime'`). 무료 사용자는 **평생 총 1개**만 등록할 수 있다. 맛보기 체험용이며, 계속 쓰려면 유료 전환을 유도하는 구조.

5. **가격·한도는 코드가 아니라 DB에**
   - 요금제 값을 하드코딩하지 않고 `plans` 테이블에 저장해, **관리자 도구에서 즉시 변경**할 수 있게 했다. 가격 정책은 시장 반응에 따라 자주 바뀔 수 있으므로 배포 없이 조정 가능해야 한다는 철학.

**한도 초과 시 동작**
등록 시 한도를 넘으면, 방금 만든 콘텐츠를 **롤백(삭제)** 하고 `HTTP 402 {error:"quota_exceeded", message, usage}` 를 반환한다. 프론트는 안내 문구를 토스트로 띄우고 사이드바 사용량 배지를 갱신한다.

**구현 요약 (파일별)**
- `database.py`
  - `plans` 테이블 + 기본 4단계 시드, `content_registrations` 원장(등록 이벤트)
  - `users` 컬럼 추가: `plan_code`(기본 free), `plan_started_at`(구독 시작일)
  - 마이그레이션 시 기존 영상을 원장에 **백필**(등록일=영상 생성일). `claim_orphan_data`(첫 가입자 데이터 인수)에서도 원장 백필
  - 함수: `get_plans/get_plan/update_plan`, `set_user_plan`, `get_usage`(주기별 사용량 계산), `record_content_registration`(멱등), `undo_content_registration`(롤백), `_period_start`(구독일 기준 주기 계산)
- `server.py`
  - `_finalize_registration(video_id)` — 콘텐츠 5개 등록 경로(YouTube·가사·텍스트·URL·파일) 공통 choke point. 원장 기록 + 한도 강제 + 초과 시 롤백/402
  - 관리자 API: `GET /api/admin/plans`, `PUT /api/admin/plans/<code>`(가격·한도), `PUT /api/admin/users/<id>/plan`(요금제 부여). `admin_list_users`에 요금제/사용량 포함
  - 사용자 API: `GET /api/me/plan`(내 사용량 + 요금제 목록)
- `templates/admin.html` — 요금제 편집 카드(가격·한도 저장) + 사용자 표에 요금제 드롭다운·사용량 pill
- `templates/index.html` — 사이드바 요금제/사용량 배지(`refreshPlanBadge`), 402 안내 문구 정규화(`api()` 헬퍼)

**알려진 한계 / 향후 결정 필요**
- **플레이리스트 자동 동기화**(백그라운드 워커)로 추가되는 영상은 현재 할당량 강제 대상이 **아니다**. 요청 컨텍스트가 없고 자동 추가라 블로킹이 부적절해 이번 범위에서 제외. → 정책(자동 추가분을 카운트할지/블록할지) 확정 후 반영 필요.
- **실결제(PG) 미연동**. 지금은 관리자 수동 부여.
- 동시 요청 레이스: 극히 짧은 순간 두 요청이 동시에 한도 검사를 통과해 1개 초과 등록될 수 있음(단일 사용자 통상 사용에선 사실상 무해). 필요 시 등록 시 트랜잭션 잠금 추가.

### 2026-07-06 · Step 3 · 구글 OAuth + 사용자별 AI 키
- **왜 OAuth**: 이메일/비번 없이 간편 로그인 제공.

- **AI 키 정책(둘 다 지원)**: 사용자 개인 키가 있으면 그것을, 없으면 **서버 공용 키로 폴백**. 배경 워커(전역 캐시 생성)는 서버 키, 사용자 상호작용은 개인 키 우선.

### 2026-07-06 · Step 2 · 멀티유저 데이터 완전 격리
- **무엇**: 7개 테이블에 `user_id` 부여 + 복합 UNIQUE 재구축(같은 콘텐츠도 사용자별 독립 보관).
- **철학(격리 방식)**: 라우트마다 조건을 다는 대신, `before_request`에서 `set_current_user()`로 스레드-로컬 컨텍스트를 설정하고 모든 DB 함수가 `_uid()`로 **자동 필터**. 실수로 격리를 빠뜨릴 여지를 구조적으로 차단.

## 전반 설계 철학 (프로젝트 공통)

- **의존성 최소주의**: 가능하면 표준 라이브러리만. (OAuth도 urllib으로 구현)
- **SQLite 단일 서버 전제**: 단순함 우선. 스케일아웃이 필요해지면 PostgreSQL 전환(문서 ARCHITECTURE 11.3에 명시). 지금 최적화하지 않는다.
- **문서 자동 갱신 규칙**: 코드를 고치면 `USER_MANUAL`/`ARCHITECTURE`/`FEATURE_SPEC` 3종을 함께 갱신(`CLAUDE.md`). 이 `DECISION_LOG`는 그 위에 **"왜"** 를 더한다.
- **구조로 실수를 막는다**: 개별 호출부에 방어 코드를 흩뿌리기보다, 공통 choke point/컨텍스트로 강제(예: 데이터 격리의 `_uid()`, 할당량의 `_finalize_registration`).
- **정책 값은 데이터로**: 자주 바뀌는 값(요금제 가격·한도)은 코드가 아니라 DB에 두어 배포 없이 조정.

## 용어

- **콘텐츠(content) / 영상(video)**: 학습 단위. 내부 테이블명은 `videos`지만 YouTube·텍스트·URL·파일·가사를 모두 포함한다.
- **등록(registration)**: 콘텐츠를 받아와 **전체학습/개별학습이 가능한 상태**가 되는 것. 할당량 카운트의 기준 시점.
- **원장(ledger)**: `content_registrations` 테이블. 등록 이벤트를 영구 기록(영상 삭제와 무관).
- **주기(period)**: 할당량이 리셋되는 단위. free=평생(lifetime), 유료=구독 시작일 기준 매월(monthly).
